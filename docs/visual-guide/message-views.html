Saved history, model input and metadata differ

A message has more than one useful view. Separating stored state, the model's prepared copy and diagnostic metadata explains why a change may appear in one place but not another.

Swipe sideways to follow the full diagram.

Only one snapshot-export arrow is drawn to keep the view clear. State hooks and tool wrappers also have snapshots when enabled. The reply path groups response guards and the graph’s merge operation.

Find out which copy changed

Date and memory hooks can add hidden messages to saved state; summarization can replace older history. Input sanitization instead adds user-input boundaries to the outgoing request copy. PII middleware can mask recognized personal data in that copy while the original stored user text remains unchanged. Request-only warnings and receipt ledgers follow the same distinction.

Metadata describes the work

Labels such as thread_id, dearflow_run_id, dearflow_middleware and dearflow_hook help locate and explain a trace. They do not automatically become prompt text. Some message metadata also has an application role: hide_from_ui marks injected context for omission from the visible conversation. To see provider-facing messages, inspect the actual model node's input.

Implementation notes and references

PII masking has a defined scope and can fail open if its redactor raises an error. Snapshot masking does not globally redact all native traces. Snapshots can be shortened; tool schemas and model settings may appear outside the model's message list.
