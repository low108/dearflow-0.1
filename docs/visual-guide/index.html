01 / Architecture / DearFlow

DearFlow turns model decisions into work

The model decides what to say or which tool to request. DearFlow prepares the messages, runs permitted tools and keeps the work moving until the turn ends.

Swipe sideways to follow the full diagram.

Responsibilities, not deployment machines. The checkpointer saves conversation messages; RunService saves run records. Memory injection and saving are shown together as one optional memory component. LangSmith is covered in diagram 07.

Follow the request from left to right

You enter through the terminal CLI or the HTTP API. RunService starts and tracks the turn, then hands it to the lead agent. The lead agent repeatedly calls a chat model and, when needed, executes tools. An optional task tool starts a helper agent and brings its report back into the same loop.

Tools act; skills supply instructions

A tool is a callable capability, such as a calculator or an enabled MCP tool. A skill is written guidance: the model first sees its name and description, then can use load_skill to read the full instructions. Loading a skill does not install a capability or automatically carry out its steps. Middleware adds checks and preparation around the work.

Lead agent
The coordinator that runs the model-and-tools loop.
RunService
The code that starts a turn, streams progress and records its outcome and token usage.
MCP
A way to connect external tool servers to the agent.
Implementation notes and references

The boxes show responsibilities, not separate computers or security boundaries. This simplified project provides no built-in shell, sandbox or virtual filesystem.

02 / Sequence / DearFlow

One request can need two model calls

A tool request is the model asking DearFlow to do something. The model usually needs another call after the result arrives so it can explain the answer to you.

Swipe sideways to follow the full diagram.

Illustrative happy path: one user turn, two model calls and one calculator execution. Time runs downward. Guards run before tool execution; exact provider behavior may differ.

Example: multiply 17 by 23

The user asks to use the calculator. On the first model call, the model requests calculator(left=17, right=23, operation="multiply"). After the guards permit it, DearFlow runs the calculator and receives 391. A ToolMessage links that result to the original tool request. The second model call can then answer using the result.

The repeating part is the model-and-tools loop

before_agent prepares the whole turn once. before_model runs before each model step; wrappers surround the model call; after_model checks its reply. Ordinary tool results return to before_model. A final answer finishes through after_agent. Interactive clarification is a special exit: DearFlow asks its question and waits for your next turn.

Thread
A conversation containing one or more turns.
Turn / run
One invocation that handles a user request.
Model call
One request sent to a language model within that run.
Implementation notes and references

This is an illustrative successful path with the calculator enabled. Exact wording, tool choice and model-call count can vary. A result may serialize as 391.0. Todo reminders and other guards can also change the route.

03 / Flowchart / DearFlow

Middleware acts at different checkpoints

Middleware is code around the agent's work. Some layers change messages; others change state, tool results, metadata or the decision about what happens next.

Swipe sideways to follow the full diagram.

Why do middleware stamps add fields to additional_kwargs?

The wrapped model box includes request preparation, the actual model and wrapper return processing. After-model guards normally run before tools. A direct clarification ends this invocation.

Before and after refer to different-sized steps

before_agent and after_agent surround the whole turn. before_model and after_model surround each model step. A wrap_model_call or wrap_tool_call hook surrounds one downstream operation: it can prepare the request, call the next layer and inspect what comes back. It is normal for a hook to make no change when its condition is absent.

Read wrappers like layers around one call

Model wrappers enter in registration order and return in reverse order. ToolReceipt is the outer layer; PII is the innermost model wrapper in the complete lead-agent chain. These are several layers around one model call, not several new model calls. After the wrapped reply returns, after_model guards can remove proposed tools or request another model step.

Why stamp a message?

A stamp is a small record attached to a message so later code knows where it came from, what it represents or what context was available. additional_kwargs is the message's dictionary of extra named fields. It is separate from its content and from LangSmith run metadata.

ToolReceiptMiddleware adds dearflow_tool_receipt to the existing ToolMessage. The tool has already returned. Its result text and call ID stay the same: no second ToolMessage or second tool execution is created by this stamp.

If the exact key is additional_kwargs.tool_calls, that is a different case: a provider adapter may preserve raw call data there while also exposing the same request as AIMessage.tool_calls. The receipt middleware does not create that provider field. Check the key and call ID before treating repeated data as another execution.

Keeping the record beside its result makes it available in saved conversation checkpoints, without mixing audit fields into the answer text. Code can later check a subagent's receipt citations without another model call. Receipts are optional: the basic tool loop can work without them, but it loses this execution record and citation evidence.

Why each receipt field exists

FieldPurpose
tool_call_idConnects the record to call_calc_1. Repeated uses of the same tool have separate call IDs.
tool_nameNames the tool. The citation checker can reject [r1 calculator] if r1 actually names a different tool.
statusCopies the returned message's success/error status. An error gets a receipt too; a receipt alone does not mean success.
args_sha256First 16 hexadecimal characters of a SHA-256 fingerprint of the arguments serialized as sorted-key JSON. A compact identifier, not another copy of the arguments.
output_sha256The same kind of short fingerprint for the returned content. The receipt contains no copy of the output text.
output_bytesUTF-8 size of that content. "391.0" is 5 bytes. Bytes are not tokens.
created_atUTC time when the middleware stamps the returned result. It is not the call's duration.
id: "r1"Added later when receipts are listed in message order. It is a citation label, not the stable tool_call_id; it is absent from the initial stamp above.

The receipt wrapper sits outside the other tool wrappers. It records the result they return, including an error message produced by error handling or content changed by redaction. The argument fingerprint uses the request seen by this wrapper. DearFlow overwrites its own receipt key rather than accepting a tool-supplied value, while preserving other additional_kwargs fields.

A receipt records a returned call and its reported status. The current citation checker checks the ID, status and optional tool-name anchor; it does not recompute the hashes or validate the answer. These short fingerprints are not encryption, a digital signature or a tamper-proof certificate. A resolved citation does not prove the user's task is complete.

Why stamp the model reply too?

WhenWhat happensWhy
1. Tool returnsStamp the existing ToolMessagedearflow_tool_receipt records this result for later audit and listing.
2. Next model requestAdd a temporary receipt list when enabledA request-only HumanMessage makes the receipt IDs readable to the model.
3. Model repliesStamp the existing AIMessagedearflow_tool_receipt_ledger preserves exactly the numbered receipts offered on that request.
4. Check a helper reportResolve its citations with codeMatch [r1 calculator] against the helper reply's preserved list, not a newly renumbered history.

Why keep another list on the reply? Suppose a reply cites [r2] for the calculator. Later, summarization removes an older r1 message and the surviving calculator receipt becomes r1. Rebuilding the list now would misread the old citation. The reply's stamped ledger freezes the original numbering. It also keeps only the entries that fit in the rendered list.

The hidden ledger message has dearflow_injected: "receipt_ledger" and hide_from_ui: true. Hidden means hidden from the chat display, not from the model. Its content is included in the outgoing request and uses prompt tokens. It is not stored as a new conversation message. The receipt list stamped on the returning AIMessage is application metadata, not another model response.

The default lead setting is receipts_render_mode: "delegation_only": a normal calculator turn can have a tool receipt without a visible-to-model ledger. The lead renders it when reading a task result in the current turn. With always, receipts are rendered whenever present; enabled subagent receipts use this mode. The list has a 2,000-character budget, dropping older entries when needed. An active render path with no receipts can stamp [] without adding a hidden message.

How to check this in LangSmith

  1. Open middleware.ToolReceiptMiddleware.wrap_tool_call (or its async equivalent). Compare calls[0].response.value with result.value: the same result content and tool_call_id remain, while additional_kwargs.dearflow_tool_receipt appears.
  2. For wrap_model_call, compare before.value with calls[0].request.value for the temporary ledger. Compare calls[0].response.value with result.value for the reply's dearflow_tool_receipt_ledger. A later inner wrapper may still change the forwarded request.
  3. Custom message snapshots allowlist the two DearFlow receipt keys. Other additional_kwargs fields may be missing from that view even when present at runtime. Provider traces and stored messages can show a different selection.
  4. Count actual tool runs and actual LLM runs to detect extra work. A metadata stamp creates neither. A rendered ledger can increase input tokens on an already scheduled model call; it does not schedule another call.

04 / Architecture / DearFlow

Each helper needs a complete task

Delegation starts a fresh agent through the task tool. The lead must include the relevant facts in the task prompt because helpers do not automatically see the lead conversation.

Swipe sideways to follow the full diagram.

Two possible task calls, shown as a conceptual handoff. Each helper contains its own model/tool loop. Context separation does not imply a sandbox.

Split work that can be done independently

For example, the lead can ask one helper to check the time in Paris and another to check Berlin. Each helper receives its own instructions, task text and allowed tools, and runs its own model-and-tools loop. Independent task calls may run in parallel when permitted. Their final reports return as tool results for the lead to combine.

A helper has narrower context and capabilities

Helpers use filtered tools and a smaller middleware chain. By default they cannot call task again or ask the user for clarification. They share the turn's token budget when that feature is enabled. The lead should inspect returned evidence: a report or a valid tool-receipt citation does not by itself prove every claim is correct.

task
The tool used to send a self-contained assignment to a subagent.
Subagent
A helper with its own instructions, context and model/tool loop.
Filtered tools
The subset of tools that a helper is permitted to use.
Implementation notes and references

Fresh context is not a process or filesystem sandbox. The asynchronous helper path enforces the configured wall-clock timeout; the synchronous path does not. Parallel work and exact task count depend on the model and configured limits.

05 / Sequence / DearFlow

Memory is saved after a turn and read later

Conversation history remembers what happened in one thread. Long-term memory separately keeps selected facts about a user so a later turn can use them.

Swipe sideways to follow the full diagram.

Illustration: “My favourite notebook colour is green”, followed later by “What is my favourite notebook colour?” The extractor may run after Turn A ends; this figure assumes saving succeeds before Turn B.

Saving is a background process

At the end of Turn A, after_agent queues the latest user and final assistant exchange. After a short batching delay, or an explicit flush, a separate extractor proposes lasting facts. Valid facts are merged into the user's memory.json. Queueing succeeded does not mean a fact has already been accepted and saved.

Recall happens when another turn starts

On Turn B, before_agent reads memory for the same user_id. If memory is enabled, nonempty and changed, it adds a hidden <memory> message to the conversation state. The model can use that context even in a fresh thread. To verify recall, check the saved fact and the later injection, then ask a question that does not supply the answer itself.

Checkpoint
Saved conversation state used to continue a thread.
Memory extractor
A background model call that selects facts worth keeping.
Debounce
A short delay that batches nearby updates into one extraction.
Implementation notes and references

Not every statement becomes a memory fact. A quick next turn may arrive before saving finishes. Extraction can fail while chat still succeeds. Background extraction normally has separate trace and token usage outside the main turn totals.

06 / Architecture / DearFlow

Saved history, model input and metadata differ

A message has more than one useful view. Separating stored state, the model's prepared copy and diagnostic metadata explains why a change may appear in one place but not another.

Swipe sideways to follow the full diagram.

Only one snapshot-export arrow is drawn to keep the view clear. State hooks and tool wrappers also have snapshots when enabled. The reply path groups response guards and the graph’s merge operation.

Find out which copy changed

Date and memory hooks can add hidden messages to saved state; summarization can replace older history. Input sanitization instead adds user-input boundaries to the outgoing request copy. PII middleware can mask recognized personal data in that copy while the original stored user text remains unchanged. Request-only warnings and receipt ledgers follow the same distinction.

Metadata describes the work

Labels such as thread_id, dearflow_run_id, dearflow_middleware and dearflow_hook help locate and explain a trace. They do not automatically become prompt text. Some message metadata also has an application role: hide_from_ui marks injected context for omission from the visible conversation. To see provider-facing messages, inspect the actual model node's input.

07 / Tree / DearFlow

Compare boundaries to see what changed

LangSmith shows the run as nested work. A middleware span records the boundary around that layer; its child handler may contain more middleware, a tool or an actual model call.

Swipe sideways to follow the full diagram.

Schematic of the calculator example, not a literal trace export. Framework spans and individual wrappers are grouped. Lines mean “contains”, not execution order; the two LLM leaves are the actual model calls.

Use the right pair of fields

For a wrapper's outgoing changes, compare inputs.before.value with outputs.calls[0].request.value. For its return changes, compare outputs.calls[0].response.value with outputs.result.value. For a before/after state hook, inspect outputs.state_update.value as a patch, then inspect a later hook input to see the merged state. A null patch can be correct.

Count actual model calls once

Wrapper spans nest around the same work, so their durations overlap. Use the turn's recorded totals or add the usage of actual model calls once each; do not add parent totals to their children. Lead-agent, helper and in-turn middleware model calls can all consume tokens. Ordinary tools and wrapper code do not consume model tokens just because they have spans.

Span
One recorded operation inside a trace.
handler_calls
How many times this wrapper invoked its downstream handler; zero can mean interception.
Inclusive duration
Elapsed time that includes the child work performed inside a span.
Implementation notes and references

Middleware snapshots must be enabled; Show All may be needed to reveal them. Missing provider usage means usage is unknown, even if a local counter remains zero. Background memory extraction usually falls outside the turn totals. Token counts and dollar cost are different measures.

About this guide

Start with the picture. Follow the evidence.

These diagrams explain supported behavior from the local source. They are not new model tests or literal screenshots of a run. Configuration, error handling and explicit routing can change a particular execution.

For exact middleware snapshots and real LangSmith screenshots, use the original 62-page middleware guide. The before-and-after companion walks through each hook. For setup and API usage, read the project README and observability documentation.

The explanation structure was informed by Sampan’s documentation: a system map, one concrete round trip and focused diagrams for ideas that need their own view. The figures were built using Cathryn Lavery’s diagram-design skill, with the DearFlow navy/teal style selected for this project.

Design choices and source audit

Source of colors and system font stacks: the existing DearFlow middleware-flow guide. Paper is a neutral #F4F6F5; ink #12283B; accent #087E83; secondary text #536675. Instrument Serif adds the skill’s editorial title contrast; Georgia is its disclosed offline fallback. There are no shadows or scripts. Each figure uses a 1280 × 720 frame with the larger presentation type scale and local horizontal scrolling on narrow screens.

Each drawing answers one question. Internal classes, every wrapper span and the complete tool inventory are grouped; diagram 03’s table retains all 14 middleware. Storage details, helper limits and snapshot caveats live in the notes. Source audit · Design receipt
