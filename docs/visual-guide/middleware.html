Middleware acts at different checkpoints

Middleware is code around the agent's work. Some layers change messages; others change state, tool results, metadata or the decision about what happens next.

Swipe sideways to follow the full diagram.

Why do middleware stamps add fields to additional_kwargs?

The wrapped model box includes request preparation, the actual model and wrapper return processing. After-model guards normally run before tools. A direct clarification ends this invocation.

Before and after refer to different-sized steps

before_agent and after_agent surround the whole turn. before_model and after_model surround each model step. A wrap_model_call or wrap_tool_call hook surrounds one downstream operation: it can prepare the request, call the next layer and inspect what comes back. It is normal for a hook to make no change when its condition is absent.

Read wrappers like layers around one call

Model wrappers enter in registration order and return in reverse order. ToolReceipt is the outer layer; PII is the innermost model wrapper in the complete lead-agent chain. These are several layers around one model call, not several new model calls. After the wrapped reply returns, after_model guards can remove proposed tools or request another model step.

Why stamp a message?

A stamp is a small record attached to a message so later code knows where it came from, what it represents or what context was available. additional_kwargs is the message's dictionary of extra named fields. It is separate from its content and from LangSmith run metadata.

ToolReceiptMiddleware adds dearflow_tool_receipt to the existing ToolMessage. The tool has already returned. Its result text and call ID stay the same: no second ToolMessage or second tool execution is created by this stamp.

If the exact key is additional_kwargs.tool_calls, that is a different case: a provider adapter may preserve raw call data there while also exposing the same request as AIMessage.tool_calls. The receipt middleware does not create that provider field. Check the key and call ID before treating repeated data as another execution.

Keeping the record beside its result makes it available in saved conversation checkpoints, without mixing audit fields into the answer text. Code can later check a subagent's receipt citations without another model call. Receipts are optional: the basic tool loop can work without them, but it loses this execution record and citation evidence.

Why each receipt field exists

FieldPurpose
tool_call_idConnects the record to call_calc_1. Repeated uses of the same tool have separate call IDs.
tool_nameNames the tool. The citation checker can reject [r1 calculator] if r1 actually names a different tool.
statusCopies the returned message's success/error status. An error gets a receipt too; a receipt alone does not mean success.
args_sha256First 16 hexadecimal characters of a SHA-256 fingerprint of the arguments serialized as sorted-key JSON. A compact identifier, not another copy of the arguments.
output_sha256The same kind of short fingerprint for the returned content. The receipt contains no copy of the output text.
output_bytesUTF-8 size of that content. "391.0" is 5 bytes. Bytes are not tokens.
created_atUTC time when the middleware stamps the returned result. It is not the call's duration.
id: "r1"Added later when receipts are listed in message order. It is a citation label, not the stable tool_call_id; it is absent from the initial stamp above.

The receipt wrapper sits outside the other tool wrappers. It records the result they return, including an error message produced by error handling or content changed by redaction. The argument fingerprint uses the request seen by this wrapper. DearFlow overwrites its own receipt key rather than accepting a tool-supplied value, while preserving other additional_kwargs fields.

A receipt records a returned call and its reported status. The current citation checker checks the ID, status and optional tool-name anchor; it does not recompute the hashes or validate the answer. These short fingerprints are not encryption, a digital signature or a tamper-proof certificate. A resolved citation does not prove the user's task is complete.

Why stamp the model reply too?

WhenWhat happensWhy
1. Tool returnsStamp the existing ToolMessagedearflow_tool_receipt records this result for later audit and listing.
2. Next model requestAdd a temporary receipt list when enabledA request-only HumanMessage makes the receipt IDs readable to the model.
3. Model repliesStamp the existing AIMessagedearflow_tool_receipt_ledger preserves exactly the numbered receipts offered on that request.
4. Check a helper reportResolve its citations with codeMatch [r1 calculator] against the helper reply's preserved list, not a newly renumbered history.

Why keep another list on the reply? Suppose a reply cites [r2] for the calculator. Later, summarization removes an older r1 message and the surviving calculator receipt becomes r1. Rebuilding the list now would misread the old citation. The reply's stamped ledger freezes the original numbering. It also keeps only the entries that fit in the rendered list.

The hidden ledger message has dearflow_injected: "receipt_ledger" and hide_from_ui: true. Hidden means hidden from the chat display, not from the model. Its content is included in the outgoing request and uses prompt tokens. It is not stored as a new conversation message. The receipt list stamped on the returning AIMessage is application metadata, not another model response.

## Tool receipts (execution record)
...

The default lead setting is receipts_render_mode: "delegation_only": a normal calculator turn can have a tool receipt without a visible-to-model ledger. The lead renders it when reading a task result in the current turn. With always, receipts are rendered whenever present; enabled subagent receipts use this mode. The list has a 2,000-character budget, dropping older entries when needed. An active render path with no receipts can stamp [] without adding a hidden message.

How to check this in LangSmith

  1. Open middleware.ToolReceiptMiddleware.wrap_tool_call (or its async equivalent). Compare calls[0].response.value with result.value: the same result content and tool_call_id remain, while additional_kwargs.dearflow_tool_receipt appears.
  2. For wrap_model_call, compare before.value with calls[0].request.value for the temporary ledger. Compare calls[0].response.value with result.value for the reply's dearflow_tool_receipt_ledger. A later inner wrapper may still change the forwarded request.
  3. Custom message snapshots allowlist the two DearFlow receipt keys. Other additional_kwargs fields may be missing from that view even when present at runtime. Provider traces and stored messages can show a different selection.
  4. Count actual tool runs and actual LLM runs to detect extra work. A metadata stamp creates neither. A rendered ledger can increase input tokens on an already scheduled model call; it does not schedule another call.

Implementation notes and references

The complete chain is a map of supported middleware, not a claim that every feature is enabled in every run. An explicit routing jump can bypass later hooks in that iteration. Subagents use a smaller chain.
