01 / Architecture / DearFlow

DearFlow turns model decisions into work

The model decides what to say or which tool to request. DearFlow prepares the messages, runs permitted tools and keeps the work moving until the turn ends.

Swipe sideways to follow the full diagram.

Responsibilities, not deployment machines. The checkpointer saves conversation messages; RunService saves run records. Memory injection and saving are shown together as one optional memory component. LangSmith is covered in diagram 07.

Follow the request from left to right

You enter through the terminal CLI or the HTTP API. RunService starts and tracks the turn, then hands it to the lead agent. The lead agent repeatedly calls a chat model and, when needed, executes tools. An optional task tool starts a helper agent and brings its report back into the same loop.

Tools act; skills supply instructions

A tool is a callable capability, such as a calculator or an enabled MCP tool. A skill is written guidance: the model first sees its name and description, then can use load_skill to read the full instructions. Loading a skill does not install a capability or automatically carry out its steps. Middleware adds checks and preparation around the work.

Lead agent
The coordinator that runs the model-and-tools loop.
RunService
The code that starts a turn, streams progress and records its outcome and token usage.
MCP
A way to connect external tool servers to the agent.
Implementation notes and references

The boxes show responsibilities, not separate computers or security boundaries. This simplified project provides no built-in shell, sandbox or virtual filesystem.
